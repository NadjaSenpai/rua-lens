# RUA Lens v0.1.0 実装計画

- 作成日：2026-07-18
- 対象仕様：[RUA Lens 設計書](../specs/2026-07-17-rua-lens-design.md)
- 対象リリース：`v0.1.0`
- 実装方式：縦切りのTDD

## 1. 到達点

この計画は、承認済みの設計をCloudflare Workers上で動く一つの製品へ変換する。

完成時には、利用者がXML、gzip、ZIP形式のDMARC aggregate reportを手動でアップロードし、ダッシュボード、一覧、詳細で正規化結果を確認できる。
管理者だけがレポートを削除できる。
元ファイルはWorkerの処理中だけ存在し、D1へは正規化した値だけを保存する。

この計画にはGitHubリポジトリの作成、Cloudflare本番リソースの作成、本番デプロイを含めない。
実装、ローカル検証、CI、第三者が再現できるセルフホスト手順までを含める。

## 2. 実装を始める前に固定する判断

### 2.1 実行環境とパッケージ管理

- Node.js 22 LTSを開発環境とCIの基準にする。
- パッケージ管理にはnpmを使い、`package-lock.json`をコミットする。
- WranglerはプロジェクトのdevDependencyに固定し、コマンドは`npm exec -- wrangler`またはnpm script経由で実行する。
- `compatibility_date`は実装開始日に設定し、依存更新とは別の変更として更新する。
- Workers型は`wrangler types`で生成し、`worker-configuration.d.ts`をコミットする。

実行時依存は`hono`、`fast-xml-parser`、`fflate`、`jose`、`react`、`react-dom`、`react-router-dom`、`recharts`に限定する。
開発依存には`@cloudflare/vite-plugin`、`@cloudflare/vitest-pool-workers`、`vite`、`vitest`、TypeScript、ESLint、Playwright、Testing Library、jsdomと必要な型定義を入れる。
バージョン番号をこの文書へ固定せず、実装開始時の互換バージョンを`package-lock.json`で固定する。

### 2.2 Cloudflare設定ファイル

Cloudflare Vite pluginは自動リソース作成を扱わないため、リポジトリには`wrangler.jsonc.example`だけを保存する。
実際の`wrangler.jsonc`はgitignoreし、ローカルセットアップ時にexampleから生成する。

exampleにはゼロUUIDと架空値だけを入れる。
本番D1は次のコマンドで作成し、Wranglerに実IDを書かせる。

```bash
npm exec -- wrangler d1 create rua-lens --binding DB --update-config
```

CIはジョブ内で`wrangler.jsonc.example`を`wrangler.jsonc`へコピーしてから、型生成、テスト、ビルドを実行する。

### 2.3 認証設定

本番では`AUTH_MODE=access`を必須にする。
`ACCESS_TEAM_DOMAIN`、`ACCESS_AUD`、`ADMIN_EMAILS`のいずれかが欠けた場合は、認証を迂回せず設定エラーとしてfail closedにする。

ローカル環境だけで`AUTH_MODE=dev`を許可する。
`.dev.vars.example`には`DEV_USER_EMAIL=developer@example.com`と架空の管理者メールを置く。
本番用exampleで`dev`を既定値にしない。

### 2.4 APIの補助エンドポイント

設計書の画面には利用者メールと管理者向け操作があるため、`GET /api/session`を追加する。
このエンドポイントは認証済み利用者のメールアドレスと`isAdmin`だけを返す。
Access JWT本体、claim全体、管理者一覧は返さない。

### 2.5 日時、ID、ページング

- D1の日時はUTCのUnix秒を`INTEGER`で保存する。
- APIの日時はISO 8601のUTC文字列で返す。
- 内部IDはWorkerで生成したUUID文字列にする。
- レポート一覧は`page`と`pageSize`を使い、`pageSize`の既定値を25、上限を100にする。
- 日付範囲は`from`を含み、`to`の翌日を含まない半開区間として扱う。

fingerprintへ使う対象domainは小文字へ正規化する。
提供組織と外部report IDは前後の空白だけを除き、大文字小文字を保持する。
五値は文字列連結ではなくJSON tupleへ符号化し、値の境界を曖昧にしない。

### 2.6 表示区分とDMARC成功

表示区分はAPIとD1で`pass`、`review`、`fail`の三値にする。
画面ではそれぞれ「正常」「要確認」「失敗」と表示する。

DMARC成功は表示区分と分けて`dmarc_pass`として保存する。
policy overrideのため`review`になったレコードでも、aligned DKIMまたはaligned SPFがpassなら`dmarc_pass = 1`になる。

### 3.2 公開interface

取り込み側の中心interfaceを次の形に固定する。

```ts
export type ReportCandidate = {
  sourceFileName: string;
  entryName: string | null;
  xml: Uint8Array;
};

export async function* extractReportCandidates(
  file: File,
  budget: ExpansionBudget,
): AsyncIterable<ReportCandidate>;

export function parseDmarcXml(xml: Uint8Array): NormalizedReport;

export function classifyRecord(record: NormalizedRecord): {
  classification: "pass" | "review" | "fail";
  dmarcPass: boolean;
};

export async function computeFingerprint(
  metadata: ReportIdentity,
): Promise<string>;
```

アップロードrouteが呼ぶinterfaceは一つにまとめる。

```ts
export async function ingestBatch(input: {
  files: ReadonlyArray<File>;
  principal: Principal;
  db: D1Database;
  limits?: IngestLimits;
}): Promise<UploadBatchResult>;
```

D1はローカルテストで実物相当を利用できるため、架空のrepository interfaceとin-memory実装は作らない。
`saveReport`、`listReports`、`getReport`、`deleteReport`、`getDashboard`を小さな具体関数として公開し、テストではmigration適用済みのローカルD1を渡す。

```ts
export async function saveReport(
  db: D1Database,
  report: NormalizedReport,
  importedBy: string,
): Promise<
  | { kind: "inserted"; reportId: string }
  | { kind: "duplicate"; reportId: string }
>;
```

AccessのJWKS取得は外部境界なので、token verifierだけにinterfaceを置く。
本番adapterは`jose`の`createRemoteJWKSet`と`jwtVerify`を使う。
テストではローカル鍵から署名したJWTを検証し、ネットワークを使わない。

```ts
export type AccessTokenVerifier = (
  token: string,
  config: AccessConfig,
) => Promise<VerifiedAccessIdentity>;
```

UIの外部境界は同一origin APIだけなので、`RuaLensApi`を一つ置く。
ブラウザーadapterは`fetch`を使い、UIテストは同じinterfaceのテストadapterを使う。

### 3.3 ストリーミングとメモリ所有権

取り込みはファイル単位、XMLレポート単位で逐次実行する。
複数ファイルやZIP内の全entryを展開済み配列として保持しない。

gzipとZIPは`fflate`のストリーミングAPIで展開し、出力chunkを受け取るたびに制限を加算する。
一つのXML候補だけは`fast-xml-parser`へ渡すために連続した`Uint8Array`へまとめる。
解析、D1保存、結果作成が終わったら、そのXMLと解析オブジェクトへの参照を次候補へ持ち越さない。

Workersのisolateメモリ上限は128 MBなので、20 MiBのXML上限は設定値だけでは保証できない。
20 MiBのXML、深い要素、多数のrecordを使った負荷テストをrelease gateにする。

ローカルのworkerdはデプロイ時のresource limitを強制しないため、資格情報なしCIは入力境界と結果だけを検証する。
128 MB制限の確認はscratch D1と`wrangler dev --remote`を使う手動release gateへ分ける。
remote実行で上限を満たせない場合は、設計書と`limits.ts`の両方を同じ変更で下げる。
scratch D1のID、remote URL、試験dataはtracked fileへ残さない。

## 4. API契約

### 4.1 共通エラー

```json
{
  "error": {
    "code": "INVALID_XML",
    "message": "DMARC aggregate reportとして読み取れませんでした。",
    "requestId": "00000000-0000-0000-0000-000000000000"
  }
}
```

`message`は画面表示可能な一般文だけにする。
XML断片、ファイル内容、SQL、stack、JWTを含めない。

### 4.2 `GET /api/session`

```json
{
  "email": "developer@example.com",
  "isAdmin": true
}
```

### 4.3 `POST /api/uploads`

multipart field名は`files`に統一する。
ファイル数、入力合計、またはrequest body全体の制限違反は`413`を返す。
requestを受理した後に判明した個別XML、ZIP entry、重複は、部分成功を維持するため通常の`200`内へ結果として返す。
個別ファイルの10 MiB超過もそのファイルのrejected結果とし、同じbatchの正常ファイルを処理する。
multipart構文が壊れてファイル単位へ対応づけられない場合だけ`422`を返す。
D1接続失敗などの基盤エラーはbatch結果へ偽装せず、一般化した`500`とrequest IDを返す。
基盤エラーより前にcommit済みのreportは残るが、再試行時のfingerprintで二重登録を防ぐ。

```json
{
  "requestId": "00000000-0000-0000-0000-000000000000",
  "summary": {
    "inserted": 1,
    "duplicate": 1,
    "rejected": 1
  },
  "results": [
    {
      "sourceFileName": "report.zip",
      "entryName": "reports/example.xml",
      "status": "inserted",
      "reportId": "00000000-0000-0000-0000-000000000001"
    },
    {
      "sourceFileName": "report.xml.gz",
      "entryName": null,
      "status": "duplicate",
      "reportId": "00000000-0000-0000-0000-000000000002"
    },
    {
      "sourceFileName": "invalid.xml",
      "entryName": null,
      "status": "rejected",
      "code": "INVALID_XML",
      "message": "DMARC aggregate reportとして読み取れませんでした。"
    }
  ]
}
```

### 4.4 読み取りAPI

`GET /api/reports`は`domain`、`from`、`to`、`page`、`pageSize`を受け取る。
レスポンスは`items`、`page`、`pageSize`、`total`を返す。

`GET /api/reports/:id`はメタデータ、公開ポリシー、record、各recordのDKIM、SPF、policy overrideを返す。
存在しないIDは`404`を返す。

`GET /api/dashboard`は`domain`、`from`、`to`を受け取る。
レスポンスはsummary、dailyTrend、dispositions、failureSources、domains、recentReportsを返す。
dailyTrendの各日は`total`、`dmarcPass`、`dmarcFail`、`pass`、`review`、`fail`を持つ。
成功率と`dmarcPass`はaligned認証で計算し、三分類の`pass`とは混同しない。

`DELETE /api/reports/:id`は管理者だけを許可する。
成功時は`204`、存在しないIDは`404`、一般利用者は`403`を返す。

## 5. D1スキーマ

最初のmigrationは`migrations/0001_initial.sql`へ置く。

### 5.1 テーブル

`reports`には次の列を作る。

- `id TEXT PRIMARY KEY`
- `org_name TEXT NOT NULL`
- `external_report_id TEXT NOT NULL`
- `domain TEXT NOT NULL`
- `period_begin INTEGER NOT NULL`
- `period_end INTEGER NOT NULL`
- `policy_p TEXT NOT NULL`
- `policy_sp TEXT`
- `policy_pct INTEGER NOT NULL`
- `policy_adkim TEXT NOT NULL`
- `policy_aspf TEXT NOT NULL`
- `imported_at INTEGER NOT NULL`
- `imported_by TEXT NOT NULL`
- `fingerprint TEXT NOT NULL UNIQUE`

`report_records`には次の列を作る。

- `id TEXT PRIMARY KEY`
- `report_id TEXT NOT NULL REFERENCES reports(id) ON DELETE CASCADE`
- `source_ip TEXT NOT NULL`
- `message_count INTEGER NOT NULL CHECK (message_count > 0)`
- `disposition TEXT NOT NULL CHECK (disposition IN ('none', 'quarantine', 'reject'))`
- `evaluated_dkim TEXT NOT NULL`
- `evaluated_spf TEXT NOT NULL`
- `classification TEXT NOT NULL CHECK (classification IN ('pass', 'review', 'fail'))`
- `dmarc_pass INTEGER NOT NULL CHECK (dmarc_pass IN (0, 1))`
- `header_from TEXT NOT NULL`
- `envelope_from TEXT`
- `envelope_to TEXT`

`dkim_results`、`spf_results`、`policy_overrides`はUUIDの主キーと`record_id`外部キーを持つ。
各外部キーは`ON DELETE CASCADE`にする。
DMARCで省略可能な`human_result`、`selector`、`scope`、override commentはNULLを許可する。

### 5.2 制約とindex

policy値、alignment値、割合、期間へCHECK制約を付ける。
`period_begin <= period_end`と`0 <= policy_pct <= 100`をDBでも保証する。

次のindexを作る。

- `reports(domain, period_begin, period_end)`
- `reports(imported_at DESC)`
- `report_records(report_id)`
- `report_records(source_ip)`
- `report_records(classification)`
- 各子テーブルの`record_id`

### 5.3 レポート単位のtransaction

親、record、DKIM、SPF、overrideのINSERTを一つの`db.batch()`へ渡す。
D1の`batch()`は途中のstatementが失敗すると全体をrollbackするため、レポート単位の原子性を保てる。

行ごとのINSERTは使わない。
配列をJSON文字列としてbindし、`json_each(?)`と`json_extract(...)`で複数行INSERTへ展開する。
D1のbind値は2 MB未満に収める必要があるため、UTF-8で1.5 MiB以下のJSON chunkへ分ける。
一つのreportで作るstatement数は40以下にし、超えたreportは`EXCESSIVE_STRUCTURE`として保存前に拒否する。

fingerprintのUNIQUE違反だけをduplicateへ変換する。
ほかのD1エラーをduplicateとして握りつぶさない。

## 6. 入力制限と拒否順序

制限値は`src/server/ingest/limits.ts`に一か所だけ定義し、クライアントの事前検証とサーバー検証が同じAPI公開値を参照する。
サーバーを正とし、クライアントの検証は操作補助に限定する。

検査順序は次のとおりに固定する。

1. 認証とrequest全体の`Content-Type`を確認する。
2. Honoの`bodyLimit`でrequest bodyを25 MiBと256 KiBの合計以下に制限する。
3. `Content-Length`がある場合は同じ上限をbody読取前に確認し、ない場合はstream読取量を`bodyLimit`で確認する。
4. multipartを読み、ファイル数、各入力サイズ、ファイル入力合計25 MiBを確認する。
5. magic bytesと先頭の空白を除いた内容からXML、gzip、ZIPを判別する。
6. 展開chunkごとにファイル別とbatch全体の展開量を加算する。
7. ZIP entry数と正規化したpathを確認する。
8. XMLを文字列化する前にサイズを確認する。
9. DOCTYPE、ENTITY、SYSTEM、PUBLIC、外部参照を事前走査で拒否する。
10. XMLValidatorとDMARC必須構造を検証する。
11. 正規化、判定、fingerprint、D1保存を行う。

256 KiBはmultipart boundary、part header、ファイル名にだけ使うtransport上限であり、ファイル入力25 MiBを増やす値ではない。
`bodyLimit`で全bodyを先に上限化してから`parseBody({ all: true })`を呼び、同名の`files` fieldを配列として取り出す。
この経路は最大約25 MiBを一時的にbufferするため、Task 16で最大batchを含むメモリ試験を行う。

XML parserでは`processEntities: false`を必須にする。
record、auth_results、policy overrideの既知pathは`isArray`で常に配列へ変換する。
最大nestingも設定し、未知要素は無視して既知の必須要素を厳密に検証する。

XMLの事前走査はDOCTYPE宣言とENTITY宣言をmarkupとして検出する。
通常のtextに含まれる`SYSTEM`や`PUBLIC`、組み込みentityの`&amp;`だけを理由に拒否しない。
DOCTYPEを全面拒否することで、その内部に置かれる外部参照も解析前に止める。

省略された`pct`は100、`adkim`と`aspf`は`r`へ正規化する。
省略された`sp`はNULLとして保存し、画面では`p`を継承する意味を示す。
message countは正のsafe integer、期間は非負のUnix秒、対象domainと送信元IPは妥当な値であることを保存前に確認する。

ZIP pathはバックスラッシュをスラッシュへ変換してからPOSIX形式で正規化する。
絶対path、drive letter、NUL、空path、正規化前後に`..`を含むpathを拒否する。
ディレクトリentryは数に含めるが処理せず、通常ファイルはXMLだけを候補にする。

## 7. テスト構成

### 7.1 Workerテスト

`vitest.worker.config.ts`は`@cloudflare/vitest-pool-workers`を使う。
`cloudflare:test`の`applyD1Migrations`で各テスト用D1へmigrationを適用する。

domain、取り込み、repository、Hono APIのテストをWorkers runtimeで実行する。
Hono routeは`app.request()`だけで済ませず、D1 bindingを含む経路は`cloudflare:workers`のdefault export経由でも確認する。

### 7.2 UIテスト

`vitest.ui.config.ts`はjsdom、Testing Library、user-eventを使う。
UIは`RuaLensApi`のテストadapterを注入し、XML parserやD1をmockしない。
テストは画面に見える文字、role、操作結果を観測する。

### 7.3 E2Eテスト

PlaywrightはVite pluginのローカルWorkerを起動し、dev authとローカルD1を使う。
テストごとに既知のDB状態へ戻し、`example.com`と予約済みIPだけを含む合成fixtureをアップロードする。

### 7.4 fixture方針

fixtureは最小の合成データから始める。
各fixtureの意図をファイル名で示し、同じ巨大XMLを複数テストで使い回さない。

最低限、次のfixtureを用意する。

- 単一recordの正常report
- 複数record、複数DKIM、複数SPF、複数override
- gzip化した正常report
- 複数XMLを含むZIP
- DOCTYPEとentityを含むXML
- DMARC以外のXML
- 必須要素欠落
- ZIP Slip path
- 破損gzipと破損ZIP
- 制限境界の生成helper

実在のDMARC reportをfixtureへ入れない。
